Reference Architecture

Intelligence Engine

An agentic pre-engagement intelligence tool for management consultants working in organization, workforce, and change. It researches a real company, grounds the analysis in a workforce dataset, and produces a briefing — pausing at five checkpoints where a consultant validates, corrects, and redirects the work.

Implemented & running Amazon Bedrock S3 · DynamoDB · CloudWatch Claude Sonnet 4.6 us-east-1

01

What It Actually Does

Not a demo harness — a working tool with real LLM research, real AWS storage, and enforced guardrails.

A consultant enters a company name. The engine verifies the company is real, loads a workforce dataset if one exists for it, then runs four LLM phases — research, organizational analysis, opportunity identification, briefing generation — before rendering a formatted HTML report. Between each phase the run pauses and waits for the consultant.

At every checkpoint the consultant can approve (optionally with direction that carries into later phases) or request a revision, which sends their feedback back to the model and regenerates that phase. Revision is a loop, not a dead end — there is no "reject and start over."

The consultant and the engineer use different interfaces. They are separate Flask blueprints in separate modules.

Engineer Console

Structural, not cosmetic

The consultant templates contain zero links to /engineer. The engineer blueprint lives in its own module with its own template family and its own base layout. In a corporate deployment it would be served behind different auth, or not registered at all in the consultant-facing process.

The Seven-Stage Workflow

Two setup phases, then four LLM phases and a render — with five consultant checkpoints woven through.

0a
Entity Verification
Before spending a single Sonnet token, a cheap Haiku call confirms the company is real and identifiable. Gibberish, placeholders, and known-fictional companies are blocked. Low-confidence names surface to the consultant for confirmation.
guardrails.check_company_exists() · claude-haiku-4-5
0b
Workforce Dataset Load
If the company has a dataset in S3, the query layer reads its profiles and postings and computes roughly thirty signals — tenure and flight risk by department, hiring velocity, hardest-to-fill roles, compensation bands. These are rendered into a compact context block injected into every downstream prompt.
datasets/query.py · DatasetQuery.summarize()
1
Company ResearchCheckpoint 1
Claude returns structured facts: headcount, revenue, CEO, segments, recent developments, workforce and organizational context. Completeness is checked and the call retried if required fields are missing. Headcount is sanity-checked against the dataset. The consultant validates and corrects.
_research_company() → research.json
2
Organizational AnalysisCheckpoint 2
Structure, workforce composition, challenges, talent risks, culture signals, and transformation readiness — grounded in the measured dataset figures rather than recalled generalities. The consultant can redirect focus.
_analyze_organization() → org_analysis.json
3
Engagement OpportunitiesCheckpoint 3
Four to six specific consulting opportunities, each with a description, expected impact, urgency, and service line. Sized against the workforce data. The consultant prioritizes or adds what the analysis missed.
_identify_opportunities() → opportunities.json
4
Briefing GenerationCheckpoint 4
An 800–1200 word briefing: executive summary, company overview, organizational landscape, challenges, prioritized opportunities, and preparation notes covering stakeholders to map and sensitive topics. All accumulated consultant feedback feeds this prompt.
_generate_briefing() → briefing.md
5
Report RenderCheckpoint 5
The briefing becomes a formatted HTML document suitable for internal circulation. The consultant reviews and approves for delivery, or requests final adjustments.
_render_intelligence_report() → intelligence_briefing.html

Feedback compounds forward

A correction at checkpoint 1 is passed into phases 2, 3, and 4. Feedback isn't consumed and discarded — it accumulates into the context of every subsequent call, and the full history is written to feedback_log.json alongside the report.

05

Synthetic Workforce Datasets

Twenty anonymized client archetypes, each with employee profiles and two years of hiring history, stored in S3.

How they are generated

A hybrid approach keeps token cost bounded while producing industry-accurate data. Bedrock generates each company's organizational template — departments, five-rung title ladders, domain skills, typical degrees, tenure and turnover characteristics, plus hiring categories with locations and remote ratios. Python then generates volume from that template deterministically, seeded per company so runs are reproducible.

The template call is split into two focused requests. A combined request reliably exceeded the output token budget and returned truncated JSON; splitting it, plus a retry that escalates max_tokens on a parse failure, made generation reliable.

The data is genuinely industry-specific

A pharmaceutical client yields departments like Clinical Development & Medical Affairs, roles like Medical Monitor, and required skills like GCP compliance, biostatistics, and regulatory submissions — not generic corporate placeholders.

What each record contains

Employee Profile
profiles.jsonl
Name, title, department, seniority, location, tenure, age, education, skills, connection count. Full job history distinguishing internal promotions from external moves. Six months of social activity with post type, topic, and engagement counts. A computed turnover risk score and an open_to_opportunities flag.
500 per companytenure-correlated risk
Job Posting
postings.jsonl
Title, department, location, work arrangement, seniority, posted date across a 24-month window, lifecycle status, salary band, applicant count, days to fill, and required skills drawn from the matching department's skill pool.

These are rendered by DatasetSummary.to_agent_context() into a compact text block that is injected into the research, analysis, opportunity, and briefing prompts. The engineer console shows this exact string, so what the model sees is never a mystery.

06

Guardrails

Fourteen rules across four categories, configured in YAML and tunable from the engineer console without touching code.

Every rule carries enabled, a severity of block, warn, or log, and its own parameters. Checks never raise on a policy failure — they return a result the caller interprets. Severity decides behavior: block halts the run, warn annotates the UI and logs, log records silently.

Input validation — before any token spend

company_name_formatblock
Length bounds, alphabetic ratio, no-vowel token detection, repeated-character limit, keyboard-run patterns, and a placeholder blocklist.
prompt_injectionblock
Scans the company and context fields for instruction-override patterns, role reassignment, and system-prompt extraction attempts.
engagement_context_lengthwarn
Flags unusually long context that would inflate token cost across four downstream prompts.

Entity verification

company_existsblock
A Haiku call confirms the organization is real. Fictional companies blocked by default; low-confidence names surface to the consultant rather than failing outright.
company_size_sanitywarn
Parses headcount from formats like ~43,000 or 40,000-45,000 and flags implausible values or large deviation from the dataset.

Output validation

pii_leakageblock
Blocks output containing SSN patterns, card numbers, or non-synthetic email addresses.
hallucination_markerswarn
Flags hedging and placeholder language — "I don't have information", "XYZ Corp", "[insert", "for illustrative purposes".
research_completenesswarn
Verifies downstream-required fields are present and retries the call before continuing.
minimum_lengthwarn
Catches truncated or empty responses that would otherwise flow silently into the report.

Cost and access controls

max_tokens_per_runblock
Hard ceiling on per-run token spend.
max_revisions_per_checkpointblock
Bounds the revision loop so a checkpoint cannot cycle indefinitely.
max_concurrent_runsblock
Limits simultaneous runs to control burst cost.
dataset_query_limitsblock
Bounds how many profiles and postings a single query returns.
cross_company_isolationblock
Asserts that a run scoped to one company never reads another's records.

Tunable at runtime

The engineer console renders every rule with its live severity and parameters, shows a violation feed across all runs, and offers a YAML editor that validates syntax before writing and hot-reloads on save. Disabling a rule takes effect on the next run without a restart.

07

Client and Run Isolation

Enforced by key construction, not by asking the model to behave.

Every storage call takes client_id and run_id as required arguments; the key is built from them.

Dataset reads follow the same rule. DatasetQuery builds every S3 key from the company_id passed in, so a query scoped to one company physically cannot return another company's records — there is no code path that constructs a key without it. Tests deliberately attempt cross-run and cross-client reads and assert they fail.

08

Separation of Concerns

What reasons, what computes, and what enforces are three different things.

Reasoning — the model

  • Research a company from its knowledge
  • Interpret organizational dynamics
  • Identify engagement opportunities
  • Compose the briefing narrative
  • Incorporate consultant feedback
  • Non-deterministic by nature

Computation — the code

  • Aggregate workforce signals
  • Compute tenure and risk statistics
  • Rank hardest-to-fill roles
  • Derive hiring velocity trend
  • Render report templates
  • Same input, same output — tested

Enforcement — infrastructure

  • S3 prefix and key construction
  • IAM scoping in production
  • Bucket encryption and TLS-only policy
  • Guardrail severity decisions
  • Token and concurrency ceilings
  • Prompts are never the boundary

Running It

# install
pip install -e ".[dev]"

# tests — no AWS required
pytest -q

# refresh credentials
aws sso login --profile intelligence-dev

# deploy infrastructure
aws cloudformation deploy --profile intelligence-dev --region us-east-1 \
  --template-file infrastructure/cloudformation/storage.yaml \
  --stack-name intelligence-engine-dev-storage --parameter-overrides Environment=dev

# generate all twenty datasets and upload to S3
python scripts/data_generation/generate_all.py --profile intelligence-dev

# run the app
python webapp/app.py
#   consultant → http://localhost:5000
#   engineer   → http://localhost:5000/engineer

# run consultant console only
ENGINEER_CONSOLE=0 python webapp/app.py

# Bedrock usage reporting
python scripts/bedrock_usage.py --profile intelligence-dev --hours 24
python scripts/bedrock_usage.py --profile intelligence-dev --cost --month-to-date

Corporate Deployment Path

How this maps into an environment where DevOps owns infrastructure and console access is restricted.

ConcernSandbox todayCorporate target
Consultant UILocal FlaskApp Runner container behind corporate SSO, scales to zero
Engineer accessSame process at /engineerSeparate service, separate auth, or unregistered blueprint
Engineering workflowClaude Code on the laptopClaude Code on an EC2 dev instance reached via SSM Session Manager — no console, no SSH keys, sessions recorded
CredentialsSSO profileIAM role attached to the compute; nothing to manage locally
DeploymentManual CLIGit → PR review → CI/CD → staging → DevOps-approved promotion
NetworkPublic endpointsPrivate subnets with VPC endpoints for Bedrock, S3, and DynamoDB
Agent runtimePython thread per runBedrock AgentCore Runtime with session suspend/resume at checkpoints

The checkpoint model is the piece that maps most directly. Today a run pauses by blocking a background thread. AgentCore Runtime suspends the session instead, so a run waiting on a consultant consumes no tokens and no compute — which matters when a real engagement briefing might sit unreviewed overnight.

Known Limits

Stated plainly, because a reference architecture that hides its gaps is not useful.

Run state is in-memory
The DynamoDB table and state manager exist and are exercised by the CLI orchestrator, but the web app keeps runs in a process dictionary. Restarting loses history. Wiring the web app to DynamoDB is the next structural step.
Research is model knowledge, not live retrieval
Company facts come from the model's training data and are bounded by its cutoff. The consultant validates and corrects at checkpoint 1, which is why that checkpoint exists. Live retrieval would be a genuine improvement.
Datasets are synthetic
The workforce data is generated, not observed. It demonstrates the pattern of grounding analysis in measured signals; it is not evidence about any real company.
provider_data_share is enabled
Acceptable for a personal sandbox with synthetic data. It must be reviewed before any deployment touching confidential client information.
No authentication
The web app is unauthenticated and intended for local use. Corporate deployment requires SSO in front of both consoles.
No CI/CD
Tests run locally; deployment is manual CLI. A pipeline with secret scanning and staged promotion is defined in the corporate architecture but not yet built.
